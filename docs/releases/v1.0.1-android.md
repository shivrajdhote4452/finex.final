## 2. Release Summary & PR #38 Parity Changes

Version 1.0.1 delivers comprehensive mobile parity with the FinEx web terminal and FastAPI backend:

1. **Authoritative Paper Order Handling & Rejection Truthfulness:**
   - Integrated `OrderExecutionService` matching web logic.
   - Backend order rejections (`status == 'REJECTED'`) preserve rejection reasons, keep trade sheets open, and strictly prevent local balance mutation or fake fill receipt generation.
   - Pending limit orders create `PENDING` receipts with no premature cash deductions or fabricated fill prices.
2. **Timeout Reconciliation & Idempotency:**
   - Every mobile order generates a unique client-side idempotency key (`mob-ord-<timestamp>-<rand>`).
   - On network timeout or disconnected response, queries recent backend order history to verify execution. If unconfirmed, the order outcome is marked `UNCERTAIN` with actionable guidance to prevent accidental duplicate orders.
3. **Truthful Market Data & Fallback Price Elimination:**
   - Removed all hardcoded fallback stock price maps (previously defaulting unknown symbols to ₹2,500.00).
   - Missing quotes, changes, or day high/low figures render as neutral `—`.
   - Genuine zero percentage changes (`0.00%`) are rendered faithfully rather than flagged as unavailable.
4. **Authentic Account Balances & Error Boundaries:**
   - Removed hardcoded fallback cash of ₹1,00,000 across overview, portfolio, and paper trading screens.
   - Network errors display honest error views with retry buttons instead of showing fabricated balances. Genuine zero cash balances (`₹0.00`) are preserved.
5. **Account Reset Safety Confirmation Dialog:**
   - Settings screen displays an explicit confirmation dialog before invoking the reset API.
   - Explains verified backend behavior: cash restored to exactly ₹1,00,000.00, open positions cleared, order history preserved for audit, and pending orders not canceled.
   - Provides clear Cancel (aborts without API call) and Confirm Reset actions, with duplicate submission prevention (`_isLoading` guard and spinner).
6. **Owner-Gated Deposit Controls:**
   - Aligned deposit controls in `transactions_screen.dart` behind `if (apiClient.isOwner)`, matching the React web interface and backend authorization contracts.

## 5. Version-Code Strategy & Architecture Switching Dynamics

Flutter's standard ABI-splitting configuration calculates version codes using multiplier offsets:
* **Universal Build:** Base `versionCode` = `2`
* **`armeabi-v7a`:** `1000 + base` = `1002`
* **`arm64-v8a`:** `2000 + base` = `2002`
* **`x86_64`:** `4000 + base` = `4002`

### Upgrade & Switching Behavior Under Android OS Rules:
1. **Upgrades Within Same Architecture (Seamless):**  
   Future releases increment the base `versionCode` (e.g. `v1.0.2` base `3`), giving `arm64-v8a` code `2003` (`2003 > 2002`). In-place updates across releases for the same variant proceed smoothly.
2. **Same-Version Variant Switching Limitation (Known Sideload Behavior):**  
   Android evaluates `newVersionCode >= installedVersionCode`. If a user installs the `arm64-v8a` build (`versionCode 2002`) and later attempts to install the Universal APK (`versionCode 2`), Android OS rejects the installation as a version downgrade (`INSTALL_FAILED_VERSION_DOWNGRADE`).  
   *Guidance:* Users who install an ABI-split variant should continue updating using that variant, or perform a clean reinstall if switching to Universal.
